# ADR-003: Dark-First Theming with a Custom `light:` Variant

- **Status:** Accepted
- **Date:** 2026-08-20
- **Deciders:** Project stakeholder (via theme toggle request)

## Context

`08_FRONTEND_STANDARDS.md` Ch.21 (THEME-002) documents the standard Tailwind convention: light mode is the default (unprefixed classes), dark mode is the override (`dark:` prefix) — its own worked example is `bg-danger-50 text-danger-700 dark:bg-danger-950 dark:text-danger-300`.

The frontend as actually built (`packages/ui/tailwind-preset.ts`, `packages/ui/src/tokens/colors.ts`) already deviated from this before this ADR was written: every shared component (`Select`, `TextInput`, `Button`, `Table`, etc.) and every screen in `apps/web` uses the `surface`/`ink` tokens **unprefixed** — dark is the default, with zero `dark:` classes anywhere in the codebase. `tailwind-preset.ts` registers a custom `light:` variant (`:is(.light &)`) and `colors.ts` already carries unused `lightSurface`/`lightInk` token objects for exactly this — the deviation was anticipated in-code but never recorded here, and no toggle exposed it to users. `app/layout.tsx`'s `<body>` was the one holdout still written the Ch.21 way (`bg-gray-50 ... dark:bg-gray-950`), which the `.dark` class it depends on is never applied anywhere — a dead code path, not a working dark mode.

The request driving this ADR is to expose a real light/dark toggle. That forces the choice: follow Ch.21 literally (rewrite every already-shipped component from dark-first to light-first), or formalize the convention the code already committed to.

## Options Considered

1. **Follow Ch.21 literally — light-first, `dark:` override.**
   - Pros: Matches the handbook as written; the standard, more commonly documented Tailwind pattern.
   - Cons: Every shared UI component and every screen shipped so far (several "completed, frozen" modules per `current-phase.md`) would need a full rewrite of its color classes, not just an addition — the base classes themselves are wrong under this option, not just missing a variant. High regression risk across the whole app for a purely cosmetic reason.
2. **Formalize dark-first + custom `light:` variant, per what's already shipped.**
   - Pros: Zero rewrite of existing dark-mode styling — every component's current unprefixed classes stay exactly as-is; only a `light:`-prefixed sibling class is *added* per color usage. Reuses `colors.ts`'s already-defined `lightSurface`/`lightInk` tokens and `tailwind-preset.ts`'s already-registered `light` variant, both of which exist for exactly this and would otherwise be dead code.
   - Cons: Diverges from Ch.21's literal wording; every new component going forward must remember `light:` is the override, not `dark:`.

## Decision

**Option 2** — dark-first with the custom `light:` variant, per explicit direction. `08_FRONTEND_STANDARDS.md` Ch.21 (THEME-002/21.3's worked example) is superseded by this ADR for this codebase: read "dark-mode variant" throughout Ch.21 as "the `light:` variant is the override," with dark as the implicit default requiring no prefix.

## Consequences

- Every shared `packages/ui` component and every `apps/web` screen using `surface`/`ink` tokens needs a paired `light:`-prefixed class (`light:bg-light-surface`, `light:text-light-ink`, etc.) added alongside its existing unprefixed one — an additive retrofit, not a rewrite.
- `app/layout.tsx`'s `<body>` classes move off the dead `bg-gray-50 ... dark:bg-gray-950` pattern onto the same `surface`/`ink` + `light:` convention as everything else.
- A `ThemeProvider` (React Context, per `08_FRONTEND_STANDARDS.md` STATE-003 — theme is one of its own listed examples of global cross-cutting state) toggles a `.light` class on `<html>`, persisted to `localStorage`, with a blocking inline script in `<head>` to prevent a flash of the wrong theme on load.
- Ch.21's own worked example (21.3) is now stale for this codebase and should be corrected in a future handbook edit to reference this ADR instead of contradicting it.
