# ADR-001: JWT Signing Algorithm and Key Material for Authentication

- **Status:** Accepted
- **Date:** 2026-08-03
- **Deciders:** Project stakeholder (via Authentication module review)

## Context

`09_SECURITY_GUIDELINES.md` Ch.6 (JWT-001) mandates **RS256** (asymmetric signing) for access tokens: the private signing key is held only by the Authentication module; any other verifying service uses the public key only and cannot forge tokens.

The repository's `.env.example` (written during Phase 00 tooling setup, before this module's security analysis) originally defined `PLATFORM_JWT_SECRET`/`TENANT_JWT_SECRET` — naming that implies a symmetric algorithm (HS256), contradicting JWT-001. This was flagged as an open conflict in the Authentication Module Specification (`engineering/prompts/02_platform/00_auth.md` §13).

## Options Considered

1. **RS256 (asymmetric), per `09_SECURITY_GUIDELINES.md` JWT-001 as written.**
   - Pros: Matches the frozen security handbook exactly. A compromised verifying service (holding only the public key) cannot forge tokens. Standard, well-supported (`jsonwebtoken` covers RS256 natively).
   - Cons: Requires generating, storing, and rotating asymmetric keypairs instead of a single secret string.
2. **HS256 (symmetric), matching the original `.env.example` naming.**
   - Rejected outright — directly contradicts JWT-001, a 🔴 Critical-severity rule.

## Decision

**RS256, accepted.** Both the access token and the refresh token are RS256-signed, each with its own dedicated keypair — the refresh token is a signed, `jti`-bearing token (not embedding sensitive data beyond identifiers, per JWT-002/JWT-005), not a plain random opaque string, so its authenticity can be verified independently of the Redis revocation lookup while remaining fully revocable via that same `jti` check.

Environment variables (`.env.example`), replacing the rejected `_SECRET` naming entirely:
```
JWT_PRIVATE_KEY / JWT_PUBLIC_KEY                       — access token signing/verification
REFRESH_TOKEN_PRIVATE_KEY / REFRESH_TOKEN_PUBLIC_KEY   — refresh token signing/verification
```
`JWT_SECRET`-style naming is not used anywhere in this module.

**Scope note:** this keypair set covers the **Tenant End User plane** only — the only plane this module builds (`engineering/prompts/02_platform/00_auth.md` §2). `09_SECURITY_GUIDELINES.md` AUTHN-003 still requires the Platform Operator plane to use physically separate signing keys; those variables are introduced later, when that realm is implemented, and must never reuse the four variables above.

**Note on `07_REST_API_STANDARDS.md` AUTH-003's "opaque" refresh token language:** AUTH-003 describes refresh tokens as "opaque." Signing the refresh token as an RS256 JWT does not weaken this rule's intent — the client still never meaningfully parses or relies on the token's contents (it is opaque *to the client*), and revocability is preserved identically via the server-side Redis `jti` check (JWT-005). This is a clarification of implementation, not a deviation from the rule's security property.

## Consequences

- Token issuance/verification code uses RS256 key pairs (private key held only by the issuing service; public key distributable to verifying middleware) rather than a shared secret.
- Local development requires a generated dev keypair (to be wired into `scripts/setup/bootstrap-dev-environment.sh` at implementation time), not a placeholder string.
- `.env.example` has been updated to reflect this decision (done, this ADR).
- A key-rotation procedure (`09_SECURITY_GUIDELINES.md` §3.6: graceful rotation, verify against current + previous key during a transition window) is required at implementation time, tracked as follow-up work under the Authentication module's Technical Design (Ch.7).
- The Platform Operator plane's separate keypair is deferred, consistent with the Authentication module's stated out-of-scope boundary.
